### Default to the reference scope; stronger guarantees require opt-in

The user directs that implementation must not be blocked on guarantees the original implementation does not provide unless the user specifically wants those guarantees. For every target, default to the selected reference implementation's documented and supported behavior for the chosen version, configuration, platform and workload, together with applicable mandatory protocol rules and explicit user requirements. Do not turn a desirable improvement, an imagined ideal service, an evaluator convenience or a generic recipe checklist into an additional mandatory product guarantee.

This rule governs every phase, shared capability, platform prerequisite, acceptance test and release gate below. Terms such as preserve, mandatory, security, complete accounting and safe cleanup do not by themselves establish that a stronger promise was authorized. Preserve explicit user decisions, including already approved differences such as independent implementation/dependency restrictions and the comparative performance floor; do not ask for them again. Baseline alignment is not permission to reproduce known vulnerabilities, violate mandatory protocol behavior, expose secrets or introduce unsafe ownership in our own code. Record a concrete security or standards conflict and its actual boundary; do not use a broad security label to silently add whole-system containment or stronger lifecycle guarantees.

Keep a compact requirement-origin and deviation table with each target's existing decision record:

| Field | Required record |
| --- | --- |
| Requirement and scope | Stable identifier, observable promise, responsible service/OS/operator boundary and relevant configuration. |
| Basis | Reference behavior with source/version evidence; applicable mandatory standard with citation; explicit user requirement with the actual decision; or optional proposed enhancement. Unknown reference behavior stays unknown, not an assumed stronger guarantee. |
| Difference | Any stronger deadline, durability, isolation, cleanup, resource-accounting, availability or platform obligation than the selected reference; identify what the reference actually guarantees and what it leaves to the OS/operator. |
| Cost and feasibility | Additional mechanism, authority, dependency, test environment and expected implementation/qualification cost; mark unproven feasibility honestly. |
| Disposition | Baseline requirement, already approved deviation, or optional/unapproved proposal, with affected acceptance and implementation tasks. |

An optional enhancement becomes a mandatory requirement only after the user explicitly adopts the identified difference and its material tradeoffs. A generic request for a secure server, approval to implement, acceptance of an unrelated change, silence, or continuation of a goal is not that adoption. Until then, keep the enhancement out of baseline startup checks, E2E assertions, dependency prerequisites and release blockers, and continue the reference-aligned solution. Ask only when the user's intended result actually depends on the choice or the user wants to consider the enhancement; ordinary implementation decisions within the baseline do not require permission.

When a proposed requirement appears infeasible, first verify its origin and whether the reference satisfies it in equivalent conditions. If it is an agent-added stronger guarantee without approval, remove it from the mandatory scope through an explicit recorded correction, preserve the old draft/evidence, and reconcile affected tests, shared profiles and handoffs. Do not spend a large implementation campaign inventing a platform to satisfy it. If the user explicitly approved it, or an applicable mandatory standard requires it, retain it and resolve the concrete feasibility issue without silently weakening it. Lack of evidence about the reference calls for bounded investigation or a stated limitation, not a new requirement by assumption.

In existing generated work, audit blockers and additional guarantees against this table before carrying them forward. A generated document or agent-authored default alone is not evidence of user adoption. This general rule does not automatically erase separately approved service guarantees or retroactively turn failed tests into passes. Publish a precise affected-scope migration; untouched historical contracts and evidence retain their identities.

### Adopted SSH lifecycle scope

The user explicitly approved “Lets relax that to what openSSHD requires” after reviewing the difference between OpenSSH session cleanup and this project's stronger all-descendant/handle/active-I/O guarantees. For this SSH target, require OpenSSH-style session/child lifecycle: real account-authorized execution; exact channel data/status; actual direct-child exit collection when it exits; release of server-owned PTY, channel, descriptors and buffers; and ordinary OS session/disconnect behavior. Account processes may survive session closure. A new SSH session must not require proof that every descendant, account handle, kernel I/O operation or passive OS allocation from the previous session has disappeared. Preserve authentication, account permissions, key/secret isolation, protocol denials, bounded daemon resources and honest pending server-owned work. The existing one-authenticated-transport/one-live-channel profile does not become an all-account-process lifetime limit.

This target-specific decision supersedes conflicting generic cleanup/cohort/whole-workload observer requirements elsewhere in the recipe for SSH only. Full descendant containment, per-job active-zero proofs, fixed 1/5/30-second whole-workload reclamation and persistent passive-domain handover are not SSH readiness prerequisites. Ordinary OS/account limits and matched environment measurements remain distinct from session-cleanup guarantees; unavailable global workload/storage observations cannot silently reinstate the removed startup barrier. Shared server-owned operations still require safe ownership until actual completion. No HTTP/Redis lifecycle, unrelated timing, crypto, production-dependency or feature-policy change is implied.

The existing implementation's precise effective requirement and acceptance migration is maintained in [ssh-openssh-lifecycle-r1](coordination/amendments/ssh-openssh-lifecycle-r1/amendment.md). Preserve historical generated inputs and their failed/untested evidence. Future generation must consume this adopted scope and revise affected SSH acceptance/task/qualification mappings explicitly. The implementation remains separately authorized under its active release task; this recipe edit is not a new documentation run or a production deployment.

## Authority and running the recipe

This recipe is the repository's primary authored artifact and authoritative specification workflow. Its outputs are exclusively Markdown files: research records, scope, target contracts, shared capability contracts and their index, design comparisons, task definitions, acceptance plans and agreement records. It does not implement or execute those documents. Implementation and evaluation are separate activities requiring an explicit user request; approving the Markdown package alone does not authorize them. Navigation files point here; they are not additional sources of policy. No prewritten target contract, shared catalog or separate planning document is required to bootstrap a new target.

Running the recipe means an agent applies this English procedure to a named target and the user's scope and constraints. It is not a claim that a standalone executable generator already exists. The run researches the target, discovers reusable contracts if present, generates the proposed Markdown specification set and presents it for agreement. It ends with the agreed documents, or a Markdown record of outstanding decisions. There is no implementation or test-execution phase in a recipe run. Generated means independently authored English documents, not copied source or invented test results. Existing evidence may be cited with its actual scope and provenance; future tests remain planned and unexecuted.

Create implementation/ and implementation/shared/index.md during an actual recipe run when producing its researched outputs. Do not pre-create a catalog or example contract merely while editing this recipe. If previous run outputs exist, inspect them and reconcile their contracts before reuse or extension. A missing output directory is a valid first-run state, not an error or a request for the user to prepare files manually. Use actual capability names, never literal placeholder names.

Record the recipe revision, target scope, user decisions, research provenance and reused contract identities for each generated specification set. Generated contracts become binding inputs for their agreed implementation, but do not independently redefine this recipe's workflow or common policy. General improvements belong in the recipe and trigger affected-output review; target-specific negotiated decisions are retained as run inputs. Preserve existing work and evidence rather than blindly regenerating over them. Repeated runs reconcile changes and preserve unchanged identities; they need not reproduce identical prose.

Existing root-level service contracts and candidate work predate this workflow. Preserve them as migration inputs, with their requirements and evidence identities, without claiming they were generated by the revised recipe. The prematurely prepared implementation-directory drafts are archived in contract-history/20261029-before-recipe-primary. Their existence does not count as a recipe run. Implementation remains paused; neither running the recipe nor agreeing to its documents resumes it.

## Purpose and output

Produce a reviewed English specification set before implementing a server. Its target document states the complete externally observable service promises; shared capability documents state reusable component promises. Another implementer and an independent evaluator must be able to work from this identified set without reading an earlier implementation. Different internals are permitted; protocol compatibility and security obligations remain fixed.

Write a target contract at implementation/TARGET/TARGET.md and each shared capability contract at implementation/shared/CAPABILITY/CAPABILITY.md. These are documentation locations, not prescribed application architecture. A target remains self-contained about its public behavior, scope, foundation and qualification promises; it also identifies the exact shared contracts and capability profiles required to build it. No other target's specification supplies hidden requirements. Shared contracts are maintained once, not copied into service folders. Keep implementation reports, executable tests and deployment inventories separate from normative specifications. Link them by stable requirement identifiers and exact specification versions.

Do not include source code, pseudocode, required algorithms for internal data structures, prescribed application libraries, process layouts or incidental configuration syntax. An explicitly approved platform and code-provenance boundary is a qualification constraint and must be stated precisely; it does not prescribe the replacement's internal design. Protocol names, status codes, file-format constraints, numeric limits and externally meaningful cryptographic identifiers are appropriate because peers and operators observe them. An operator interface must expose the required settings. Fix the wire interface, file formats, operator-visible semantics and error behavior claimed by the profile. If configuration or command-line syntax is explicitly part of compatibility, describe its required grammar and semantics in English; otherwise an adapter may express equivalent settings. Implementation variation must not change the declared interface.

Apply this rule to every Markdown file, including research notes and test descriptions. Repository names, source links, test identifiers and vulnerability identifiers are provenance, not implementation requirements. Do not embed copied source, patches, exploit programs, shell commands, configuration snippets or pseudocode. Describe inputs, effects and observations in English. Any executable fixtures produced later belong outside Markdown.

## Execution protocol: given a target

This protocol controls specification preparation only. Every authored output of a recipe run must be a Markdown file, including indexes, revision identities, checkpoints and decision records. Do not generate source code, scripts, configuration files, fixtures, executable evaluators, binaries, JSON manifests or raw benchmark and fuzz artifacts. Do not build, run, benchmark, fuzz or deploy a candidate or reference server as part of the recipe. Use read-only research tools and existing source, documentation and evidence; source repositories are research inputs, not copied output trees.

The numbered checklists later in this recipe define what the generated Markdown must require of a future, separately requested implementation and evaluation activity. Instructions to measure, test, fix or qualify in those checklists are obligations to describe in English, not actions to execute during the recipe. Agreement does not change this output boundary. Checking generated Markdown for consistency, links, completeness and requirement coverage is part of the recipe.

The initiating input is TARGET: the product or interface to implement. Resolve its authoritative source repository, pinned revision and intended public compatibility. Collect the user's scope, exclusions, workload, deployment assumptions and existing decisions. Propose missing choices and record them as provisional; ask only when an unresolved choice materially changes scope, authority, compatibility or spending. A product name alone does not authorize its entire feature set. For nginx, Redis and SSH in this repository, preserve previously agreed scopes and limits as migration inputs.

Use implementation/ as the canonical output directory. A mention of implementations/shared means this same intended shared catalog, not permission to create a second directory. TARGET and CAPABILITY below are placeholders replaced with actual names. Running the recipe creates the following records as needed; editing this recipe creates none of them. Short related records may be sections of one document, provided the run record identifies their location and status unambiguously.

Prefer a compact document set. Keep each target contract and each shared capability contract distinct, with the shared index and required target run records. Consolidate related research, vulnerability discovery/triage/applicability, acceptance/task planning and review records into clearly identified sections when they share an owner and revision lifecycle. Create another supporting file only for a distinct authority, owner, lifecycle or a substantial navigation benefit; document that reason in the index. Do not create one file per checklist merely to demonstrate compliance. Every obligation still needs a discoverable location and stable identity; consolidation must preserve provenance, reviewability and the distinction between normative promises and evidence. Historical experiments remain immutable and are not reorganized retroactively.

Distinguish a fresh recipe-only run from a migration. In a recipe-only run, this document and the named targets are sufficient starting inputs; do not seek private history, old contracts or prior experiment outputs when the initiating instruction excludes them. References here to unavailable history are limitations, not requirements the agent can reconstruct. Public primary-source research and outputs generated during this run remain permitted. An existing deployment cannot be declared preserved without its supplied requirements or explicit scope reconciliation. Record each choice as an explicit user requirement, mandatory protocol behavior, a recipe requirement, a new provisional policy, or an unavailable historical decision. Never silently replace an explicit requirement with a convenient default. In a migration, preserve the supplied prior promises and map any proposed changes for agreement.

### Clarification checkpoints and decision ownership

Maintain one discoverable Markdown decision ledger, shared across a multi-target run where useful. It may be a section of an existing record rather than a new document. Give each question a stable identity, source, decision owner, plain-English question, recommended answer and alternatives with consequences, affected requirements and consumers, dependent work, independent work that can continue, checkpoint and current status. Record the actual answer and its provenance, then revalidate the affected documents. A recommendation is not an accepted answer.

Classify open items before asking: product, authority and spending choices belong to the user; technical questions answerable from standards or research belong to the agent; measurements and implementation assurance belong to future separately authorized evaluation. Do not ask the user to determine a protocol rule, invent a cryptographic fact or resolve an arithmetic contradiction. Research and present feasible options when a technical limitation creates a real product choice. Do not convert all routine technical choices into user approval requirements.

Use three clarification checkpoints. After initial scope discovery, ask about missing choices that materially change the research direction, authority or compatibility. After research and approach comparison, batch the remaining product choices with evidence, recommendations and tradeoffs. Before final agreement, present the exact proposed Markdown set, accepted decisions, changes and any remaining blockers. Keep batches small and coherent, normally one to three questions; combine related target choices rather than repeatedly asking the same question. Reuse answers already supplied and do not request permission again for authorized work.

Each question must permit one coherent answer. Do not bundle independent compatibility, authority, durability and spending choices into a single acceptance question. Combine consumers only when they truly share the same decision and consequences. Present a concise recommendation and concrete alternatives, linking the exact proposal rather than asking for blanket acceptance of a large package. Record partial answers against their individual decisions; agreement to one item does not answer its neighbors. Technical fixes proceed without another product-approval request. Bring back genuine product choices only after preparing feasible, reviewable alternatives.

Ask earlier if proceeding would materially misdirect dependent work or assume unknown authority. Accumulate nonurgent questions until the appropriate checkpoint. Continue independent research and drafting while awaiting answers; mark conditional branches as provisional. Silence, elapsed time, a preselected recommendation or an instruction to run the recipe is not agreement to a proposed choice. Do not execute work that requires an unanswered decision. Agreement to a scope choice does not establish final document agreement or authorize implementation.

If the execution environment cannot deliver questions interactively, publish the pending batch in the Markdown ledger and surface it through the supervising agent or final handoff. Keep independent work moving within the declared budget. A supervisor may relay actual user answers but must not invent approval. An unanswered question is a reason to stop its dependent branch, not to abandon unrelated achievable research. Record which checkpoint occurred, which questions were actually presented, and which remain only drafted.

### Implementation order: end-to-end tests, working service, then optimization

The default objective of a separately authorized implementation is a working solution to the user's core workflow. Establish executable acceptance before writing production candidate code, then implement the smallest safe vertical slice that makes those tests pass. Component completeness, model tests, source volume and build counts do not establish that a service works.

| Gate | Required future implementation work | Evidence required before proceeding |
| --- | --- | --- |
| E2E-0: runnable environment and acceptance harness | Define a small set of real user journeys and their negative controls. Install the independently authored harness in the approved disposable test environment and wire it into the repeatable local or CI runner before candidate implementation. Check client, account, storage, privilege and observation prerequisites upfront. | The harness runs, a suitable reference or independent positive control establishes its valid path, and negative controls demonstrate that wrong results fail. Record the candidate's expected initial failure or absence. Missing authority/tooling is an explicit environment blocker, never a skipped passing row. |
| E2E-1: first useful vertical slice | Implement only the prerequisites and service behavior needed for those journeys, retaining required authorization, isolation, correctness, durability and safe failure. For each subsequent feature or defect, add or reproduce its acceptance case before implementing it. | A real independent client completes the actual user workflow through the normal candidate path in the declared environment. Required effects, output/status, cleanup and a subsequent useful operation are observed. A mock backend, refusal-only path, protocol-only connection or internal test cannot satisfy this gate. |
| E2E-2: functional coverage and robustness | Expand the same suite across the promised feature scope and essential denial, cancellation, restart, recovery and resource cases. Implement toward the remaining failing cases. Run the smoke journeys on every affected integration. | All core workflows work, essential safety invariants hold, and missing broader qualification is reported separately. A newly failing core journey returns the work to functional repair. |
| E2E-3: measured optimization | Profile successful representative end-to-end work, rank material costs, and use targeted component experiments only where evidence justifies them. Preserve the functional baseline and validate each selected change through the same user journeys. | Measured normal-service improvement with functional and safety regressions excluded. Component wins alone are insufficient. Required efficiency floors remain release gates, not a reason to optimize a service that cannot perform its basic job. |
| E2E-4: full qualification | Complete the agreed security, resource, failure, interoperability, statistical performance and final fuzzing campaigns on the actual selected artifacts and environment. | Report a qualified scope only when its mandatory gates pass. A working development service is not automatically fully qualified or production-deployed. |

The initial harness must be small enough to establish the core product path early; it is not a demand to implement the complete adversarial, statistical and fuzz matrix before the first service code. Harness and disposable-environment preparation are the first engineering tasks. Each later feature gets its externally observable acceptance case before its implementation. Validate evaluator failures separately from real product failures, preserving both. Candidate absence or refused startup stays a visible failing or unavailable core journey, not a successful substitute behavior.

Identify the deployment and authority model before a large implementation investment. Before calling an environment or observation requirement a blocker, identify its reference, mandatory-standard or explicit-user basis. If it is only an unapproved stronger enhancement, keep it optional and continue the baseline path. If a genuinely required environment cannot be provided, or an adopted observation has no implementable mechanism, produce a concrete supported-platform proposal and resolve that dependency before expanding its implementation. Continue independent functional work whose harness is ready. Do not spend the blocked interval polishing unrelated performance by default, accumulate generic backend interfaces, invent stronger environmental guarantees, or silently weaken an adopted contract to make a test pass.

For a multi-service effort, require a working core journey for every in-scope service before a broad optimization campaign. Allocate available agents to the missing functional paths, acceptance harness and enabling environment first. An exception for performance work is narrow: a measured cost must directly prevent a core acceptance case from completing within its required bounds, or the user must explicitly prioritize an independent performance objective. Record the blocking case, bounded hypothesis and exit criterion; such work ends when that functional obstruction is resolved. Merely having a failing final efficiency score is not an exception.

For SSH, the initial journeys include authorized public-key login and real command execution with exact stdin/stdout/stderr and exit status, a real interactive shell/PTY with resize, denial of unauthorized access, and cleanup followed by another useful command. For HTTP they include real static delivery and the declared proxy/TLS paths; for Redis they include actual command/reply behavior and the declared persistence/restart path. Use the selected scope and required security boundaries without copying production or upstream test implementations. A successful startup-refusal test may verify a guard, but the corresponding useful-service case remains failing or blocked.

Every progress update leads with which core journeys run, which still fail or cannot run, and the next change that will make one work. Distinguish harness readiness, functional usability, optimization and full qualification. Surface a missing platform or authority decision at E2E-0 rather than leaving it buried in a later qualification list. End-to-end test deployment means the approved test environment and runner; it does not itself authorize production deployment, paid provisioning or privilege changes.

### Research source without importing its design

Analyze the target's source to discover reachable behavior, trust boundaries, dependency responsibilities, test intent and historical failure classes. Keep source revisions and provenance references. Do not export implementation excerpts, patch instructions, private layouts or an upstream design blueprint into the generated Markdown or implementation handoff. Extract observable properties in independently expressed English, then challenge those properties against standards and the selected profile. Inspect comparable implementations to avoid treating one project's incidental choices as requirements.

Select tests by what their assertions constrain. Preserve every applicable public-interface and security property regardless of how many upstream tests express it. Tests of private layouts, internal helper behavior or incidental execution structure must be re-expressed through observable behavior or rejected with a reason. Do not drop useful coverage to make an implementation look different. Reuse scenarios and independently author new test code; never copy upstream test bodies. Public standard vectors and independently run external tools retain their existing allowance.

Separate research and implementation handoffs. A research role may inspect upstream source; a design or implementation role should work from the sanitized behavioral record, standards and agreed contracts. Use a separate context without inherited upstream excerpts when available. If that separation cannot be provided, record the actual exposure and limitation in the agreement package instead of claiming independent contexts. Existing project-owned components may be reused after provenance and suitability review; that does not authorize copying upstream production code. Evaluators record their own exposure and retain independently constructed cases.

### Identify dependencies by responsibility

The approved basic foundation is precise: pinned compiler-supplied Rust standard library and disclosed compiler support, libc, libm, libgcc_s, the ELF loader and the Linux kernel. Standard-library collections and ordinary facilities fall within that pinned baseline. The word basic, or a library's small size, does not admit an additional third-party structures, parser, scheduler, crypto or TLS package. No external crypto or TLS implementation is permitted in production. Required crypto and TLS behavior must be supplied by qualified project-owned components under the same standard algorithms and protocol obligations; features cannot disappear because their implementation is missing.

Inspect upstream dependencies as evidence of responsibilities, not as a shopping list or a required decomposition. Map each responsibility to the allowed baseline, a suitable existing owned component, a proposed owned shared capability, or service-specific owned work. Follow indirect helpers and providers. Review existing shared contracts before choosing a new name, and reopen the map if an alternative approach needs a capability not previously accounted for.

### Compare and select approaches without prescribing internals

Each of the at least three approaches must be a credible way to satisfy the same proposed public contract. Explain in English its high-level responsibility boundaries, authority and isolation properties, expected resource behavior, overload and cancellation behavior, reusable capabilities, verification effort and main uncertainties. Do not include code, pseudocode, private signatures, fixed process layouts, chosen internal data structures or upstream implementation details. Different names or arbitrary constants do not count as distinct approaches.

First screen every approach against hard constraints with a recorded requirement-origin basis: required behavior, exclusions, permitted foundation, provenance, security boundaries and adopted resource obligations. An optional stronger guarantee cannot make an otherwise baseline-conforming approach ineligible. Mark an approach that fails an actual hard constraint ineligible rather than allowing speed or novelty to compensate. Rank eligible approaches against criteria declared before scoring: ease of security review, clarity of ownership and failure behavior, plausibility of meeting the adopted performance and resource gates, testability, compatible shared reuse, maintenance cost and substantive independence from upstream choices. Explain tradeoffs and use security reviewability and fewer unresolved assumptions to resolve ties. Do not fabricate numerical measurements; anticipated performance and distinctiveness remain hypotheses until evaluated.

Select the best-supported eligible approach as a provisional implementation direction, not as proof of superiority. Record why it was selected and what later evidence would require revisiting it. The design review is nonnormative rationale. The target contract states observable promises and must still permit another conforming internal design. A preferred approach does not silently add public scope, remove obligations or mandate upstream architecture. New shared needs discovered here return to Phase 2 before agreement.

For each pair of approaches, name a consequential design choice and explain how it changes the anticipated verification burden, resource tradeoff or failure handling while preserving the same public promises. Ask whether both descriptions merely restate safety properties every conforming implementation needs. If one ordinary design could satisfy all three descriptions without making the claimed different choices, the comparison has not established three alternatives. Refine the alternatives or record the shortfall; do not manufacture numerical rankings or mandate private layouts to make them look different. High-level rationale remains nonnormative and must not smuggle design choices into the behavior contract.

### Run state, checkpoints and resumption

The generated run record identifies the current phase, completed outputs and exact revisions, pending decisions, agreed scope, responsible owners, unresolved findings, permitted next documentation action and any unresolved research or review items. Update it at phase boundaries and interruption. Record recipe changes and their affected phases explicitly. A source identity not yet available is marked not built; a test not yet run is untested, never filled with invented evidence.

On resumption, read the run record and verify the referenced files and agreement against their identities. Reuse valid completed work. If inputs or agreed promises changed, identify the affected phases and revalidate those outputs before advancing; do not silently inherit approval or restart every phase. A resumed recipe run remains Markdown-only even after specification agreement. Changed public promises, authority, foundation or qualification thresholds require a revised document agreement. Work to implement the package requires a separate explicit user request and is not a resumed phase of the recipe. An unchanged rerun needs neither duplicate contracts nor repeated approval.

Define research completion before starting: named interfaces and repository revisions, relevant test families, advisory sources and retrieval date, comparable projects, expected records, finite time or effort budget and a source-access failure policy. Completion requires dispositions for the declared coverage, not certainty about every possible vulnerability. If the budget expires with required coverage missing, report the gap and request the needed scope or budget decision; do not call the research complete. Undefined behavior, incompatible requirements and unknown required authority are blockers. Explicit residual uncertainty about undiscovered defects is recorded for review and is not an impossible demand for proof of perfect security.

Track actionable research, pending user decisions and future implementation evidence separately, each with the next concrete permitted action and affected phase. Discovered records and retrieved CVE counts are not reviewed-applicability counts. Maintain dated coverage totals without letting repeated generic open rows substitute for source review. Continue achievable independent research rather than stopping early merely because drafts exist or another branch awaits an answer. No need to consume unused budget after the defined documentation work is complete. An early incomplete handoff must identify the actual blocking dependencies, access failures or stopping instruction and remaining independent work; a six-hour ceiling is not evidence that six hours were used. ### Define the permitted foundation

Permit project-owned runtime code, a pinned compiler-supplied Rust standard library and its documented supporting runtime, and the native platform consisting of libc, libm, libgcc_s, the ELF loader and the Linux kernel. The standard-library exception was explicitly approved by the user. Record the compiler, standard-library artifacts, target and supporting code identities, including incorporated upstream components. Outside that baseline, prohibit third-party runtime implementation code regardless of packaging: registry dependencies, vendored source, forks, translations, static archives, dynamically loaded objects, copied header bodies, generated implementations and hidden fallback providers. A project-owned component qualifies through provenance, not its name, repository location or license. Only the allowlisted native shared libraries may be required or loaded by the service; reused project-owned code must not introduce an extra runtime shared library. Interface declarations and mandatory ABI values derived from approved platform documentation are compatibility data; this does not permit copied executable implementation bodies.

External clients, declared proxy origins and authenticated user-selected command workloads retain their own trust boundaries; they must not become concealed providers of the server's implementation. Operating-system administration and independent evaluation tools are separately inventoried, rather than silently counted as project-owned server code. Build and evaluation tools may use third-party dependencies as tools, provided their implementation bodies are not embedded in the production artifact outside the approved baseline. ### Require substantive independence without changing the protocol

Implement production behavior from standards, mathematical definitions, English interface contracts and independently chosen designs. Do not copy, translate, mechanically transform or cosmetically rename an upstream implementation. Renamed functions, changed formatting, reordered code or arbitrary replacement constants do not establish independence. Record what reference material was consulted, previous implementation exposure, meaningful design alternatives and the rationale for the chosen representation, state transitions, validation and resource policies. Separate values into four classes. Follow standard nonce derivation and uniqueness rules, including deterministic counters where specified. - A deadline and byte, work or storage bounds where applicable.
- The recovery observation that shows subsequent legitimate work still succeeds.
- The independent observer and source provenance, or that the policy is original.
- Its requirement-origin disposition and, for a stronger-than-reference guarantee, the explicit user adoption. An original proposed policy is optional until adopted; a finite test budget is not automatically a production guarantee.

The same fields may be written as compact English paragraphs rather than repeated headings. A response code alone rarely proves a security property: a forbidden upstream may already have been contacted, or a protected file may already have been disclosed. Observe those boundaries directly.

For each limit test the value below the boundary, exactly at it, above it, and cumulative use through many small inputs. State units and accounting: decrypted bytes versus wire bytes, a whole connection versus one request, shared totals versus per-client totals. Test equivalent inputs split and coalesced across network reads. State when a deadline starts and which events can extend it.

An example of the required specificity is: a request that attempts to escape an authorized document root receives the declared rejection, returns none of a separately prepared secret marker, does not contact an upstream, and is followed by a successful ordinary request within the recovery deadline. The specification must also enumerate the path forms and filesystem races to exercise.

### Challenge guarantees and their prerequisites

For each security, consistency, durability and availability guarantee, identify what the service can observe, which actors may interfere, and what cooperation, authority or platform behavior the promise requires. Construct a counterexample in plain English under the stated threat assumptions, including interference already in progress before the request and interference after apparent completion. Distinguish an observable byte-level guarantee from an application-level notion such as a complete published version or an acknowledged durable operation.

Do not assume that a named snapshot, repeated metadata check, language choice or copied buffer establishes the promise. Explain the required observable publication or commitment boundary without prescribing its implementation. If the guarantee cannot be justified under the proposed assumptions, research feasible alternatives and negotiate any necessary product or operator obligation. Never silently weaken an existing promise, assume cooperation from an actor declared hostile, or retain an impossible guarantee to appear more secure. Document feasibility reasoning and residual implementation uncertainty separately; neither is a runtime proof.

For cancellation and cleanup, first establish which outcomes the reference actually owns and which remain ordinary OS, account or operator responsibilities. Distinguish stopping new admission, withdrawing server-granted authority, requesting termination, observing workload termination and reclaiming application and operating-system resources; do not require all of them merely because they can be named. State a deadline and observer for each adopted outcome. A successful termination request does not prove that every descendant or device operation has stopped, but proof of all such completion is not automatically a service obligation. Before treating a missing observer or infeasible completion deadline as a blocker, apply the requirement-origin check. For an explicitly required stronger guarantee, prepare a concrete supported-environment or revised-contract choice. For an unapproved enhancement, keep it optional and continue baseline behavior. Within the adopted responsibility boundary, preserve truthful residual reporting, bounded server-owned work and recovery; never relabel an actual in-scope failure as an exceptional host condition merely to pass.

A cleanup deadline must not silently end an adopted cleanup responsibility. Pending server-owned work and outstanding server operations remain owned until their declared release conditions are observed. Distinguish that obligation from proving reclamation of all user workloads or passive OS allocations; require aggregate residual accounting and continuing workload observation only where the reference scope or an explicit user decision includes them. An expired timer or absent process is not proof that every operation ended, and session completion must not be described as such proof. For in-scope pending obligations, define bounded observation, retained records and authorized retry/escalation without unlimited server state. Distinguish measured normal-case targets from reporting deadlines, and do not promise eventual completion without a platform progress assumption. Define populations, observation uncertainty and failure criteria before making a timing claim. A configured timeout is not automatically a guaranteed syscall-return, scheduler-resumption or physical-reclamation deadline.

### Define one shared resource-lifecycle policy

During a recipe run, discover or generate implementation/shared/resource-lifecycle/resource-lifecycle.md for adopted responsibilities and register its exact revision and affected consumer profiles in implementation/shared/index.md. Reconcile an existing equivalent responsibility instead of creating a competing definition. Shared reuse must not enlarge a consumer's responsibility beyond its reference scope or explicit user decisions: stronger workload containment or OS-reclamation profiles are opt-in, not inherited defaults. A shared contract describes observable obligations, not a required crate, record per allocation, scheduler, data structure, operating-system API or process layout. This instruction creates no generated output while merely editing the recipe.

Distinguish three resource categories in the scope analysis: application-owned resources; outstanding operations or workloads that can still consume resources or exercise authority; and passive operating-system retention. For each, record whether it is inside the adopted service guarantee or belongs to the OS/account/operator. For in-scope categories, define owner or accounting domain, finite allowance, release condition, observation, failure disposition and recovery. An out-of-scope category needs an honest responsibility statement, not a fictional zero count or a new mandatory runtime observer. Memory returned to an application pool is reusable capacity, not proof of reduced RSS or kernel reclamation. Unknown active work cannot be called passive merely because a handle closed, a process disappeared or an observer failed.

| Obligation | Observable promise |

| Uncertainty and saturation | Bound unresolved records, retries, retained memory and diagnostics. Unknown active work keeps its affected capacity. Aggregate passive accounting must remain bounded under repeated churn and survive the end of individual connection records without an ever-growing historical ledger.

Every consumer references the shared IDs and supplies its adopted resource mapping, commitment/authority rules and deadline profile. If adopted, identify precisely which resources and outcomes it covers, its population, clock uncertainty and observation rule; the cohort is not a statistical guarantee about arbitrary future workloads. Previously user-approved stricter promises remain in force. Drain deadlines, connection lifetimes and durability obligations are separate; continued responsibility does not promise eventual progress by a permanently stalled platform.

For each target require an English resource table covering owner/domain, resource category, counted unit, acquisition, peak/cumulative bounds, abandonment trigger, release evidence, residual transfer, deadlines, saturation behavior and acceptance IDs. Account for the table's intended responsibilities without mandating equivalent per-object runtime metadata. Preserve legitimate service and the applicable efficiency floor for cleanup and overload as well as ordinary work.

## Coverage checklist 5: Define finite limits and realistic capacity qualification

Encode the following obligations in the generated Markdown for future implementation and evaluation. This checklist does not authorize executing them during the recipe.

Choose concrete acceptance settings independently of production capacity claims. Account for connections, pending handshakes, active requests, upstream work, input bytes, output bytes, buffered data, temporary disk, source records, logs and idle state. Count all resource use attributable to admission, retained history and eventual cleanup, regardless of the internal representation. State whether capacity is shared across all listeners and service instances. Resource limits describe observable consumption or test-environment constraints; they must not require a particular buffering, storage or scheduling design.

Define predictable overload behavior and a recovery deadline. Ordinary descriptor exhaustion or a full queue must produce bounded rejection or deferral, not process death. Clearly separate this from forced termination by the operating system or attacks outside the declared host resource envelope.

Capacity evidence must record hardware, operating system, memory budget, descriptor limits, configured caps, real simultaneous arrivals, duration, peak resource use, legitimate-work latency and recovery. Choose performance targets before comparing implementations. Do not declare that a configured connection cap is a measured throughput result, and do not import SSH capacity figures as web-server capacity figures.

The resource-lifecycle contract governs release and residual accounting. Capacity plans must include steady repeated churn, finite pending-cleanup saturation and independently observed recovery; neither full per-connection historical reservations nor sampling-only zero-residual assumptions establish a feasible bound.

### Check interacting limits before freezing numbers

For every numeric bound, state the counted unit, direction, scope and lifetime, including whether it counts encoded or decoded bytes, framing and cryptographic overhead, retained or cumulative data, service or operating-system costs. Identify operations that consume several budgets and explain which limit takes precedence. Review maximum legal inputs, their required outputs, pending replies, transactions or batches, concurrent work, retained history and cleanup across target and shared contracts. A component profile cannot promise a maximum that its consumer silently makes unusable.

Construct concrete English boundary cases with arithmetic accounting: an admitted operation at its legal maximum, multiple individually legal operations whose combined cost reaches a shared bound, and a combination that cannot be admitted. Define whether work is refused before effects, deferred within a deadline, or canceled with a precisely defined outcome after commitment. Include compound responses and protocol overhead rather than comparing only payload sizes. Do not promise that all per-client maxima can coexist if the aggregate envelope cannot support them; specify admission and useful-service expectations instead.

Give every conflict an explicit resolution and acceptance scenario. Reconcile deadline precedence, legal output sizes and state transitions as well as memory and descriptor totals. Operator validation must reject incompatible settings atomically; blanket wording that invalid settings are rejected does not substitute for identifying the incompatible combinations. Preserve required capability maxima or obtain an explicit scope revision. These are specification feasibility checks, not new performance measurements or prescribed allocation algorithms.

### Separate functional defaults, capacity and throughput

Keep three declared profiles distinct: small deterministic functional limits; expanded simultaneous-connection settings; and active-work throughput settings. Increasing one profile's connection ceiling must not silently remove byte budgets, deadlines or other protections. Operator-selected settings must be positive and finite, with invalid combinations rejected atomically. Record the effective operating-system descriptor allowance and all service-owned descriptor use; resource exhaustion must remain recoverable even when the configured connection ceiling exceeds available descriptors. Configuration syntax and the means of obtaining the allowance remain implementation choices unless explicitly part of compatibility.

For each target, define separate concurrency profiles for the states actually required: transport admission, pending handshakes or preauthentication, authenticated connections, and active operations. State the counted unit, entry and exit events, useful progress or responsiveness check, hold duration where applicable, relevant deadlines, finite resource budget, exact-limit and above-limit behavior, independent legitimate control and recovery observation. Report state transitions without double-counting a connection as additional retained capacity. Successful admission is admission evidence only, not proof of useful sessions or completed work.

For a simultaneous-arrival test, stage independent clients before one shared release and record actual start skew. Validate generator capacity, available source addresses and ports, network state and client deadlines. Verify each counted item with the observation appropriate to its declared state. For retained application sessions, complete an application exchange on every counted connection, keep the same connections usable through the declared hold, and complete a second exchange. For a preauthentication profile, use protocol-appropriate bounded progress or a valid subsequent transition without requiring every peer to authenticate. Silent peers that should time out belong to a separate bounded admission-and-expiry scenario, not responsive-session capacity. Count permitted maintenance traffic separately and never extend server deadlines merely to keep a capacity experiment alive.

Preserve the SSH workload of many unauthenticated attempts and at most one authenticated user; its preauthentication capacity tests must not become many-user login tests. Web and Redis profiles define their own applicable connection and operation states. Apply the existing performance ratios to comparable useful work in the same declared state and keep target-specific absolute bounds where the reference has no equivalent behavior. This distinction does not weaken simultaneous-arrival, overload, recovery or performance obligations.

Increase offered concurrency through predeclared powers of two where practical, then test the exact configured ceiling and a burst above it. Distinguish attempted arrivals, admitted work, successful exchanges, retained connections and deliberate refusals. Compare retained useful capacity with the reference under equal allowances, and report full-count success separately from a comparative pass. Follow release with ordinary recovery and resource observations. These are tested counts within a host envelope, not theoretical operating-system maxima.

### Define a fair comparison and its completion rule

Select supported shared operations, payload sizes, concurrency levels, connection reuse, TLS settings, durations, repetitions and warm or cold state before qualification. Give both services equal declared CPU and host-resource allowances. Reference configuration may adapt policy settings but must not enable an excluded capability or weaken a required boundary for the candidate. Alternate or otherwise predeclare service order, run competing measurements separately, and distinguish a weak generator from a service limit. Internal diagnostics must be reported separately from uninstrumented comparison rates.

Pin the original reference product and release, including relevant security fixes. Do not substitute a deliberately slow reference or alter it after seeing unfavorable candidate results. Match externally meaningful work: completed bytes, retained dataset and cardinality, authentication, cryptographic strength, persistence acknowledgement, permissions, deadlines and transport. Resource-accounting settings may differ where their meanings differ; explain the translation and keep the same physical envelope and useful work. Additional candidate processes, helpers and attributable resource use belong to the candidate total. Upstream or generator costs must not disappear from the report when work is moved out of the measured service.

Measure useful successful work rather than accepted sockets, attempted requests or error responses. Define the statistic in words, including how repetitions are summarized and compared. Every mandatory workload must independently meet its declared tolerance; a favorable overall average cannot conceal a failing row. A short screen selects candidates but cannot replace the full matrix or a sustained run. Preserve individual ranges and report a narrow margin as narrow. Predetermine the treatment of invalid runs and additional repetitions; retain all attempts instead of repeating until a favorable sample appears.

Throughput tolerance does not relax correctness, byte or memory bounds, forbidden side effects, deadlines, continuity or recovery. A latency histogram starting after connection setup is not admission-inclusive end-to-end latency. Identify closed-loop measurements that omit the delay of independently arriving work. Report request latency, setup latency and overload-control latency in their actual scopes; missing measurements remain gaps.

Treat the environment as part of the comparison. Observe available network state, connection-tracking pressure, source-port availability and listener drops where applicable. A harness or host-path failure must not be assigned to the service without evidence. If isolation or privileges change, apply the same environment to both services, disclose excluded paths, and begin a new comparison series. Do not combine rates from different environments or grant the candidate extra authority to make it pass.

### Apply the seventy-percent efficiency floor

Interpret approximately seventy percent as a definite minimum of seventy percent for qualification, without an additional rounding tolerance. Efficiency is a collection of independently enforced measures, not a composite score. For lower-is-better costs, seventy-percent efficiency permits at most the reference cost divided by 0.70, approximately 1.43 times that cost. It does not mean thirty percent more cost. Each self-contained service contract must include these definitions:

| Measure | Comparison and passing requirement |
| --- | --- |
| Useful throughput | Candidate correct, completed operations or complete bytes per second are at least seventy percent of the paired reference under equal resource allowances; define the complete workload cycle |
| Useful simultaneous capacity | Candidate retained, responsive application connections or active work are at least seventy percent of the paired reference under equal allowances and deadlines; preserve any stricter existing capacity requirement |
| CPU efficiency | Total service user and operating-system CPU time per correct completed workload cycle is no more than the paired reference cost divided by 0.70; measure intentional rejection separately per correctly rejected attempt |
| Memory efficiency | Whole-service idle, steady-load, peak and post-recovery resident memory each cost no more than the paired reference divided by 0.70 at the same useful dataset, connection population and work rate; report incremental and attributable host memory separately |
| Latency | Each p50, p95 and p99 for legitimate work, connection setup and intentional rejection is no more than its comparable reference percentile divided by 0.70 and meets the service's absolute deadlines |
| Overload and recovery | At matched hostile offered load, legitimate useful throughput, cost and latency meet their applicable comparison gates; ordinary overload preserves process continuity and bounds, and recovery meets the absolute deadline and takes no more than the reference time divided by 0.70 where measurable |

Compare CPU, memory and latency at matched offered work and useful state within both services' healthy operating range, as distinct from their respective maximum-throughput runs. Do not compare a mostly rejecting candidate with a fully working reference as if it were more efficient. For overload, deliberately refused work is a separate outcome and never counts as successful business work; preserve a legitimate control. Match attack mix, arrival rate, source distribution and limits. Native policies without an equivalent reference need their own absolute resource, security and recovery gates; identify the noncomparable property before results are known and retain every shared-path comparison. A reference crash or invalid result is not a candidate performance pass.

Use the same predeclared repeated-run statistic for each paired measure and retain every individual observation and range. Fix minimum sample counts, timing resolution, variability criteria and any additional-repetition rule before final runs. A result whose uncertainty crosses its threshold is inconclusive, not a rounded pass. A zero, unresolved or below-resolution reference denominator cannot produce a meaningful ratio; improve measurement or retain the gap with the absolute bound. A constrained generator, unavailable host accounting or missing required workload is a disclosed evidence limitation, never a passing measurement. Whole-service residency gates do not imply complete host-memory attribution. Report each gate separately as passed, failed, inconclusive or untested. One failing mandatory row prevents an overall efficiency claim even if others are much faster.

### Specify a reproducible statistical decision

Explain how connection reuse, shared clients and temporal correlation affect independence. Name a suitable established method with authoritative provenance where needed, and specify its choices rather than delegating them to an evaluator's defaults. This constrains evaluation outcomes, not server internals or a required tooling library.

Specify exactly how intervals and point estimates yield pass, failure or inconclusive for higher- and lower-is-better gates, including equality at the threshold. Predeclare additional repetitions and how all attempts contribute. A phrase such as independently assessed uncertainty or variation over ten percent is insufficient without the calculation and unit. Challenge the rule using small English observation examples at, below and above the threshold and around the repeat trigger, plus a correlated or insufficient-sample case. Two evaluators given identical observations must reach the same classification. These examples establish document consistency only, not measured performance or statistical validity for an unidentified workload.
