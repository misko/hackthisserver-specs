# Bounded stream delivery capability

Identity: stream-r2. Document agreement: Draft. Implementation evidence: Untested for every STREAM requirement. Component owner: future shared transport maintainer. Proposed maintained source home: shared/bounded-stream/. No source exists in this experiment. Initial consumer: nginx WEB and ORIGIN roles; later consumers must negotiate matching limits and authority without importing web policy. Allowed foundation is owned code, pinned compiler-supplied Rust standard library/support and the permitted libc, libm, libgcc_s, ELF loader and Linux kernel only. No application transport/scheduler library or hidden helper is permitted. This component depends only on that baseline and OS entropy when a higher protocol explicitly needs it; it provides no cryptography itself.

Purpose is finite byte delivery across hostile peers, with explicit authority, isolation, lifetime, cancellation, deadlines and accounting. Inputs are opaque bytes and operator-authorized transport endpoints; outcomes are exact ordered bytes, bounded deferral, explicit error or definitive transport end. It does not define HTTP, Redis, SSH, user identity, application commit/rollback, address bans or egress policy. Consumer authority is never enlarged by a convenient transport option.

Consumer settings name positive finite total connections, retained input/output, cumulative per-exchange bytes, work/deadlines and relevant OS envelope. Supported byte-exchange profiles are WEB/ORIGIN (up to 9 MiB serialized HTTP reply and the target's independently counted origin/request framing), Redis (ordinary reply 4 MiB, EXEC reply 65 MiB, pending ordinary output 128 MiB per connection) and SSH (66 KiB framed packet, 64 MiB cumulative channel content per direction, separately counted transport framing). These are explicit consumer profiles, not a universal 16 MiB message cap that would make Redis EXEC unusable. Framing/crypto overhead remains separately charged and must fit the consumer envelope. No consumer is promised simultaneous use of every per-peer maximum. A smaller consumer limit is a declared profile restriction; an operation at that profile's legal maximum must still fit mandatory framing and reply, or settings are rejected before publication. The consumer owns admission and public error codes. A stream never implies that data has been consumed by the receiving application merely because transport acknowledged it.

All scenarios are Planned and Untested, with owner shared transport evaluator. They require success, malformed/irrelevant opaque input handling by consumers, boundary, exhaustion, interruption and legitimate recovery. Test binary interpretation only in the owning application parser; a stream must not interpret opaque content as commands. Consumer role parameters are normative only when its exact contract is agreed. Recursive dependency graph is acyclic: service or TLS to this capability to baseline. Changes to a shared promise need a revised identity and affected direct/indirect consumer review; an additive profile cannot silently expand another consumer's limits/defaults. Residual uncertainty: kernel buffering/accounting and application abandonment evidence require independent OS observations; residency alone cannot establish complete cleanup.

Revision r2 preserves STREAM-01..06 and all consumer byte/profile maxima, clarifying continuing cancellation responsibility under STREAM-02/03. Targets supply exact cadence, attempt/log costs, pending limits and operator outcome. Independent peers/OS observers distinguish termination requests, application release and actual attributable reclamation; passive kernel retention remains reported/charged separately from live-work completion. TLS and all service consumers require profile/integration review; no runtime evidence transfers.
