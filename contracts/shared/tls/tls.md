# Owned TLS capability

Identity: tls-r3, Redis-compatible profile extension of the unagreed nginx r1 draft. Document agreement: Draft. Implementation evidence: Untested. Owner: future shared TLS maintainer. Proposed single maintained source home: shared/tls/. Prerequisites: crypto-r3 TLS profile, stream-r2 and the exact approved native/compiler baseline. All cryptography and protocol behavior outside the baseline is owned; OpenSSL or another helper/provider is not allowed in production. External TLS clients/reference tools remain evaluator tools.

Purpose: authenticated TLS application byte transport for operator-bound identities. W13 is the nginx client-facing server and optional origin-client profile, TLS 1.3 only. R13 is the matching Redis server TLS 1.3 profile with no HTTP application identity/ALPN; R12 adds Redis server TLS 1.2 only. No TLS 1.2 default, 0-RTT, PSK/session resumption, session tickets, client-certificate login, renegotiation, certificate automation or network revocation fetching is supplied by W13. R12/R13 also exclude those optional features and cannot become web defaults. Inputs are hostile records/handshakes and operator-installed certificate/key/trust identities. Application authority appears only after the required authenticated handshake; unsupported negotiation refuses rather than falling back to plaintext.

Primary standards: current [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.txt), predecessor [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) for source history, certificate validation [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html), service identity [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html), and [RFC 9325](https://www.rfc-editor.org/rfc/rfc9325.html) security guidance. The [dated mandatory coverage ledger](research.md) records successor/errata reconciliation. TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384, X25519 and secp256r1 are supported. Required signatures are rsa_pkcs1_sha256 for certificates, rsa_pss_rsae_sha256 for CertificateVerify/certificates and ecdsa_secp256r1_sha256; they cannot disappear because one fixture chooses only RSA. Optional ChaCha20/Poly1305 is excluded by the proposed bounded algorithm profile, with interoperability/efficiency risk disclosed. This is not a FIPS-validation claim.

TLS1.3 post-handshake KeyUpdate remains required even though tickets and post-handshake client authentication are excluded: authenticate its order and request value, update traffic keys before use, return a requested update as specified without unbounded update loops, and enforce key-use/sequence limits. Map this to TLS-01/02, AS-TLS-01/02, with total post-handshake control bytes at most 256 KiB per consumer exchange and at most 32 received KeyUpdate messages per minute; excess control work terminates within the active consumer deadline. Standard-compatible compatibility ChangeCipherSpec is ignored only in its allowed window with its required value; it never advances authentication. Unknown ClientHello extensions/parameters are ignored where the standard requires, while duplicate/prohibited/missing required extensions produce defined alerts. Certificate chains are DER X.509 with RSA 2048–4096 or P-256 public keys and supported SHA-256 signature schemes; unsupported trust/key/critical-extension content fails closed, not a generic claim to validate every certificate type. Operator key format may differ but must express the exact selected identity without upstream CLI syntax.


Certificate-profile clarification under TLS-03/05/06: operator-installed trust anchors do not come from the peer. Validate signed-content/signature/key binding, issuer path, time, CA/basicConstraints/path length, key usage and serverAuth EKU, relevant DNS/IP/directoryName constraints and recognized critical extensions before origin-client application authority. Combined permitted keyUsage bits are not rejected merely for being combined. Reference identities are configured ASCII DNS/A-label or numeric IP; use SAN DNS-ID/IP-ID of the correct type, no Common Name fallback. Certificate wildcards match only a complete leftmost DNS label and one label at that position, never partial labels, IP strings or arbitrary suffixes. Name constraints apply to relevant names present, not just the name selected as identity; unsupported critical/constrained forms fail closed rather than bypassing constraints. No email service identity is provided.

The proposed bounded certificate profile does not perform policy-specific trust validation; following RFC9618 section6, critical policy-related extensions are rejected as unsupported, while ordinary unconstrained valid chains still work. This explicit proposal has no final user adoption. No path can accept id-alg-unsigned as a validated certificate signature. Apply RFC9608 noRevAvail consistency checks even though automatic revocation fetching is excluded: it cannot accompany a CA identity, CRL pointers or OCSP access pointer. There is no online/offline CRL/OCSP-validation capability claimed in this version; operator trust removal/reload is explicit, and an unknown revoked status cannot be represented as verified fresh revocation information. Future CRL support reopens RFC10007 and its authority/bounds/scenarios. These rules do not require any private path-processing data structure or upstream algorithm.

R12 additionally requires a compatible signature_algorithms offer and standard TLS1.2 signed transcript/envelope without MD5/SHA1 fallback, under RFC9155. RFC10015's TLS1.2 static RSA and finite-field DH/DHE prohibitions are retained; RSA signatures in ECDHE_RSA are not RSA key transport. AS-TLS-03/05/06 and AS-TLS-12-01/02 include every clarified valid/refusal/boundary/recovery case in the dated research ledger, with independently prepared certificate/key/constraint oracles and explicit reference deviations. All W13/R12/R13 direct and indirect consumers need the corresponding integration replay; SSH receives no certificate/TLS obligation.

All scenarios are Planned, evidence Untested, owner independent TLS evaluator. Success, malformed, boundary, exhaustion, interruption and recovery are required for every profile. Profile parameters and consumer totals remain independently enforced; larger component capabilities do not expand a service's authority or limits. Changes require one responsible owner, explicit direct/indirect consumer review, exact new revision and replay decisions. Source context was exposed to upstream material during this run; a future independent implementer must receive English behavior and standards, not those excerpts. Current selected-role mandatory mapping and record arithmetic are documented in research.md; any future certificate/extension/profile expansion reopens its coverage. No runtime assurance is implied.

Revision r3 binds stream-r2 continued delivery cleanup/accounting. TLS-01..06/TLS-12-01..03, algorithms, certificate limits, W13-only1.3andRedisR12/R13wire/default promises are preserved; this dependency update does not introduce a new protocol feature. Pending TLS delivery cannot lose its finite charges after a deadline. All affected consumer identity/cancellation/resource/performance/final-fuzz replays remain future and Untested.

The target-selected TLSconsumer profile supplies the same finite cancellation cadence, attempt/record/log budgets and pending-charge authority as its stream-r2profile; TLS adds no hidden unlimited cleanup queue or independent release-success assumption. TLS-04/05scenarios observe actual release and retain pending attribution after a missed deadline.
