# TLS mandatory behavior and profile research

Identity: tls-research-r1. Retrieved 2026-10-29 UTC. Research, not a new normative authority. All runtime evidence Untested. Current TLS1.3 authority is [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.txt), July 2026, replacing RFC 8446. HTML access failed initially; official text and IETF metadata succeeded, so no permanent source blocker is inferred. [Errata](https://www.rfc-editor.org/errata/rfc9846) was rechecked. Verified technical item 9040 corrects section E.2: without supported_versions, legacy TLS1.2 may negotiate only on the explicit TLS1.2 legacy version; lower/other versions abort. Reported items 9042/9043 remove obsolete TLS1.1 wording from downgrade signalling; this profile already excludes TLS1.1. Reported 9161 distinguishes syntactically representable empty CertificateRequest extension vectors from mandatory signature-algorithm sender behavior; this profile excludes client-auth requests. Reported editorial 9157 clarifies Main Secret capitalization. Reported items are retained as reported, not silently treated as verified wire changes. Earlier provisional errata number 9156 was corrected to 9161 after complete page reconciliation. RFC 8446 predecessor errata are context; current text plus verified 9040 govern.

TLS1.2 sources: [RFC 5246](https://www.rfc-editor.org/rfc/rfc5246.html), [RFC 5289](https://www.rfc-editor.org/rfc/rfc5289.html), [RFC 8422](https://www.rfc-editor.org/rfc/rfc8422.html), [RFC 5746](https://www.rfc-editor.org/rfc/rfc5746.html), [RFC 7627](https://www.rfc-editor.org/rfc/rfc7627.html), [RFC 9325](https://www.rfc-editor.org/rfc/rfc9325.html). RFC 9325 section 4.2 explicitly discourages the old static-RSA mandatory suite; the proposed profile implements its ECDHE/AEAD alternatives, not obsolete static-RSA/CBC. Section 3.5 requires secure renegotiation signalling and Extended Main Secret support even when actual renegotiation is disabled. RFC 9846 Appendix D renames secrets/extensions in prose but preserves historic PRF labels/wire behavior.

Coverage applies to the proposed W13/R13/R12 roles, not every TLS extension or trust ecosystem. Shared component has no product-specific CVEs as an unbuilt owned component; analogous nginx session/identity, Redis pending TLS lifetime, SSH crypto/packet and standard TLS failure families supply planned invariants. Future kernel/libc/compiler/provider scanner review requires resolved production identities and never substitutes for application logic. Native/algorithm timing, secret lifetime and implementation correctness remain future evidence.

TLS-r2 impact review: W13 retains TLS1.3-only, no resumption/client-auth/early data and the same bounds; R13 has same transport semantics with Redis authority above it; R12 is additive and required only by Redis. SSH has no TLS dependency. crypto-r3 adds needed standard algorithms without new runtime providers. All consumer integrations and resource/performance/fuzz replays remain Untested.

## Final certificate and TLS1.2 current-update coverage

The final targeted review checked the RFC Editor update lists and errata catalogs for the selected certificate, identity and TLS1.2 roles. This extends the initially broad certificate row with explicit observations; it is not a full PKI ecosystem or source audit. All retrievals were public read-only research on2026-10-29. No certificate peer or test service was run.

| Current authority / inspected scope | Behavioral disposition, affected promise and future observation |
| --- | --- |
| [RFC10015](https://www.rfc-editor.org/rfc/rfc10015.txt), sections2–6, July2026, updates RFC9325 and TLS1.2 suite definitions | Static RSA, finite-field DH/DHE must not negotiate in TLS1.2; static ECDH discouraged. R12's ECDHE_RSA/ECDHE_ECDSA AES128GCM choices already avoid these. An RSA signature is distinct from RSA key transport. TLS-12-01/AS-TLS-12-01 retain appropriate legacy-offer refusal and valid ECDHE neighbor; no omission of a required modern capability. |
| [RFC9155](https://www.rfc-editor.org/rfc/rfc9155.txt) | TLS1.2 signature negotiation requires signature_algorithms and excludes MD5/SHA1; server key-exchange signatures cannot use them. TLS-12-01/02 and AS-TLS-12-01/02 now explicitly exercise missing/signature fallback rather than inheriting the old SHA1 default. This does not deprecate all HMAC-SHA1 usages in other protocols or resolve SSH-R5. |
| [RFC5280](https://www.rfc-editor.org/rfc/rfc5280.html), sections4.1,4.2,6,7 and [RFC6818](https://www.rfc-editor.org/rfc/rfc6818.html) | Decode bounded DER, verify matching signed content/algorithm/key, validity, complete path to an operator trust anchor, issuer/subject binding, CA/basicConstraints/path length, key usage/EKU and relevant name constraints. A self-signed peer does not create a trust anchor. Preserve permitted explicitText encodings and standard DN/name comparison; do not mistake certificate signature value for another field. TLS-03/05/06, AS-TLS-03/05/06. |
| [RFC9549](https://www.rfc-editor.org/rfc/rfc9549.txt) supersedes8399; [RFC9598](https://www.rfc-editor.org/rfc/rfc9598.txt) supersedes8398 | DNS comparisons and constraints use standard A-label/ASCII case-insensitive label boundaries; changing a suffix inside a label cannot satisfy a constraint. The service reference-name profile takes DNS ASCII/A-label or numeric IP input; there is no email login/identity role. Email/other name forms never grant TLS service identity. Required constraints on names present in a chain still apply: reject before authority when their meaning cannot be processed safely, rather than ignoring a critical constraint because the service uses DNS. TLS-03/AS-TLS-03 includes constrained intermediate, extra constrained SAN, Unicode/malformed encodings and valid neighbors. |
| [RFC9525](https://www.rfc-editor.org/rfc/rfc9525.html), sections4–6 | Use configured reference identity, SAN DNS-ID or IP-ID of the right type, not a peer-chosen name or Common Name fallback. Supported certificate wildcard matches only a complete leftmost label and one label at that position, not a partial label, IP or multi-level suffix. DNS reference input remains ASCII/A-label; operator display/IDN provisioning is not peer authority. TLS-03/AS-TLS-03. |
| [RFC9608](https://www.rfc-editor.org/rfc/rfc9608.txt) | noRevAvail cannot appear on a CA certificate or with contradictory CRL/OCSP location extensions; these combinations make a certificate invalid even though network revocation fetching is excluded. A noncritical extension is not automatically semantically harmless. TLS-03/AS-TLS-03 adds every forbidden combination and a valid leaf neighbor. |
| [RFC9618](https://www.rfc-editor.org/rfc/rfc9618.txt), sections3,6 | Prevent policy-processing resource amplification. The bounded profile proposes no policy-specific trust validation; the standard explicitly permits that choice only with rejection of critical policy-related extensions. No graph/tree/layout or upstream repair is prescribed. Unsupported critical policy constraints are a safe refusal, while ordinary valid unconstrained chains remain accepted. TLS-03/05, AS-TLS-03/05. This narrower profile choice remains unaccepted with other certificate/profile choices. |
| [RFC9925](https://www.rfc-editor.org/rfc/rfc9925.txt) | Unsigned-certificate placeholder cannot be accepted as a signature in a validated path. Peer-supplied unsigned/self-signed objects cannot grant trust. Operator anchor authority is separate from peer proof. TLS-03/AS-TLS-03. |
| [RFC10007](https://www.rfc-editor.org/rfc/rfc10007.txt) | CRL-validation update requires keyUsage/cRLSign on a v3 CRL issuer. No online/offline CRL-validation facility is claimed by this finite profile, and no certificate URL triggers fetching. Operator trust removal/reload remains the explicit mechanism. A future CRL profile must reopen this requirement, its input/storage/crypto/authority bounds and native/tool review. Exclusion is not a promise of automatic recognition of a revoked certificate without operator information. |
