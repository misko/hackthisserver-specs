# Owned standard cryptography capability

Identity: crypto-r3, compatible unagreed draft extension for Redis TLS1.2, SSH modern algorithms and mandatory SSH implementation coverage after nginx discovery. Document agreement: Draft. Implementation evidence: Untested. Owner: future shared cryptography maintainer. Proposed single maintained source home: shared/cryptography/. No implementation is supplied. Purpose is standard cryptographic results and key/entropy boundaries for the declared TLS and SSH profiles. Prerequisites: approved baseline and Linux secure entropy. No external cryptography/TLS provider, kernel crypto offload, helper or remote delegation is allowed. Rust compiler baseline and native allowances are the same precise foundation as the target; their shared ancestry is disclosed.

TLS profile requires SHA-256, SHA-384, HMAC, HKDF with required TLS labels, AES-128-GCM and AES-256-GCM, X25519 and secp256r1 ECDH, ECDSA P-256/SHA-256, RSA-PSS with SHA-256, RSA-PKCS1/SHA-256 certificate and TLS1.2 ECDHE_RSA handshake signatures and the TLS1.2 SHA-256 PRF/Extended Main Secret computations. Mandatory TLS1.3 signature/group minima are explicitly retained. SSH reuses SHA2/HMAC/X25519/RSA and adds the profile below, without adding those choices to web/Redis. Standard identifiers, mathematical constants, parameter encodings and nonce/key derivation rules remain unchanged. Algorithm addition is not permission for custom cryptographic schemes. This capability does not define certificate trust policy, protocol transcript ordering, application authentication, key provisioning or arbitrary user commands.

Per-case deadline is the consuming protocol's finite remaining deadline, never an indefinite independent allowance. No component test pass establishes TLS transcript, certificate or service correctness. All acceptance IDs require valid recovery after refusal, exhaustion and interruption, independent stimuli/negative controls and exact future source/binary/environment identities. Draft extensions must name new IDs and affected consumers; unchanged TLS profile must not acquire another protocol's mandatory choices. Runtime assurance, algorithm side-channel behavior and performance remain unresolved future evidence, not completed by this Markdown.

CRYPTO-01 through 05 remain common component-owned promises, not duplicate service definitions. TLS additions are compatible algorithm requirements within its profile; SSH additions have the new IDs above. Direct TLS and SSH consumers plus indirect nginx/Redis are named in the catalog. Any genuinely common promise change reopens all affected profiles, not merely the newest caller.

The earlier [mandatory-algorithm proposal](../../sshd/research.md#mandatory-implementation-rationale) is now integrated into this unagreed crypto-r3 draft for review, not approved or qualified. It closes the formerly omitted responsibility without enabling legacy wire negotiation. Source exposure and extra attack-surface/maintenance uncertainty remain disclosed. An implementation must not claim mandatory coverage simply because this table exists; all listed results/provenance/integration remain future evidence. The extra component/denial budget is reconciled in the current task/provenance/acceptance proposals. Current tls-r3 consumes only this revision's TLS profile; prior TLS algorithms, record policy and web1.3-only behavior remain unchanged.
