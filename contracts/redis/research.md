RESP3 does not require accepting every RESP3 type as a client command argument: commands retain arrays of binary string arguments. The server must generate the correct selected response type for each supported command. Negative/overflow framing and client-sent push/attribute/streamed aggregate data cannot become commands. HELLO version switch is connection-local, completed atomically; failed authentication/negotiation cannot leak state. In RESP2 subscription mode, only the supported subscription-control/PING/QUIT forms are legal; RESP3 subscribed clients can use ordinary supported commands, with pushes separate. Queue-time errors dirty the transaction and cause EXECABORT; run-time command errors occupy their array position and do not roll back other valid commands. WATCH invalidates for a relevant modification or expiry after watch, including changes later restored to equal bytes; watching an already absent expired key does not invent a prior change. Blocking pops inside a transaction do not wait. These technical rules are researcher-owned, not user questions.

Remaining required research is tracked by REDIS-R1 through R4, full catalog reply/options mapping and census reconciliation. No current evidence proves implementation correctness, durability or performance.

## Approaches and capabilities

### Redis approaches and shared dispositions

Identity: redis-design-r2. Nonnormative rationale. All alternatives must meet the same finite RESP2/RESP3 contract, durable acknowledgement boundary, allowed foundation, isolation and resource gates. No benchmark exists. Criteria declared before ranking: security reviewability, ownership/failure clarity, plausible complete-cycle efficiency/resource compliance, independent testability, compatible sharing, maintenance cost and meaningful independence. Hard violations are ineligible.

| Approach | Consequential choice preserving public behavior | Failure/resource/verification tradeoff | Screen and rank |
| --- | --- | --- | --- |
| Commit each accepted mutation independently | Make each successful mutation or EXEC a distinct durability completion before its acknowledgement. | Simple acknowledgement relation and fewer shared-failure outcomes; likely higher storage synchronization cost. Read-only commands need no extra durable commit. Cancellation after commitment remains an unknown-to-client success. | Conditionally eligible, second; efficiency risk on small durable writes. |
| Share durability completion across concurrent independent commands | Several already ordered accepted mutations may become durable together; no command is acknowledged before its own durable state is included. | Amortizes expected storage cost at added queue/deadline and failure-attribution complexity; atomic EXEC and command reply association remain unchanged. | Conditionally eligible, preferred for plausible full-cycle efficiency while retaining one documented acknowledgement boundary. No batch size or internal layout prescribed. |
| Treat complete state publication as the durability unit | A new complete recoverable state becomes the durability basis for admitted mutations, rather than independent or shared command completion units. | Clear externally recoverable version boundary but potentially expensive large-state publication and retention; interruption/reclamation and maximum dataset cost need independent evidence. | Conditionally eligible, third; more assumptions about large-state efficiency. |

Pairwise: independent versus shared completion changes whether unrelated durable commands wait on a common completion event, trading write cost for queue/failure review. Independent versus complete-state publication changes the unit whose persistence justifies acknowledgement, shifting cost with dataset size. Shared versus complete-state publication changes whether durability tracks accepted command groups or complete state versions, with different restart and retention evidence. All require atomic commands, proper expiry, safe authentication and correct RESP; those complementary safeguards are not alternatives. For clarity, the first two alternatives advance an existing recoverable state without requiring publication of a complete replacement state as their completion unit; they differ in whether unrelated commands share completion. The third makes that complete replacement publication the required completion unit. This separates the comparison dimensions rather than counting a per-command full-state publication twice. One design cannot make all three exclusive completion choices for the same command. Selection is provisional; evidence of deadline, recovery or efficiency failure reopens it without weakening acknowledgement semantics.
