Identity: nginx-acceptance-r2. Document agreement: Draft. Every scenario is Planned and every implementation requirement Untested. ## Requirement-to-scenario mapping

Each scenario includes valid neighboring traffic, an independent outside observer, the contract's below/exact/above/cumulative boundaries and recovery. Configuration adapters express settings only; they cannot repair malformed input or change assertions. Use an ordinary independent HTTP client, an independent TLS client and controlled byte-precise peers. Shared library ancestry of clients must be disclosed. Observe the origin and protected files independently of response status. Validate clocks, framing, trust stores and marker visibility before attributing a failure. An orderly close or reset can prove definitive abandonment where permitted; a timeout alone cannot. Keep unrevealed independent cases separate from implementation exposure.

## Finite workload expansion, replacement r2

Use qualification-r2 STAT-01 through 04 and EXEC-01 for every comparable row, all distinct70% metrics and absolute bounds. The following finite expansion replaces the unaccepted1356/164 Cartesian proposal; it does not inherit any runtime evidence. All supported forms still have functional scenarios A-NGX-01 through 16.

Baseline TLS1.3 means AES128GCM/SHA256, X25519, RSA2048 identity and one presented leaf to an independently configured anchor; baseline origin is plaintext. Bulk supplements keep that setup profile unless explicitly selecting another cipher/role/joint maximum. No tool negotiation default supplies a hidden setting.

Seven application families: full static GET; HEAD plus conditional GET; single-range GET plus ordinary neighbor; fixed-origin GET; fixed-length proxy body/echo; chunked proxy body/echo; correctly rejected malformed/over-limit request plus independent useful GET. A complete cycle includes every reply, origin effect and cleanup; bodyless response sizes refer to underlying representation. Rejection is separately costed and cannot count as useful throughput.

For each family use both clear HTTP and baseline TLS1.3, and these ten explicit (size, offered client population, reuse) settings: (1 byte,1, fresh), (1 byte,16, retained), (16 KiB,1, retained), (16 KiB,16, fresh), (maximum,1, retained), (maximum,64, fresh), (1 byte,64, retained), (maximum,16, retained), (16 KiB,64, retained), (maximum,64, retained). Maximum is8 MiB representation or 1 MiB request content; malformed inputs have corresponding invalid-field/over-limit values, not a legal body mislabeled invalid. Thus7×2×10=140 rows. Add fresh-only setup plus small GET, two transports×populations1/16/64=6 rows; setup has no fictional retained-handshake axis. Baseline146 ordinary rows.

TLS1.3 configurations are two ciphers(AES128GCM/SHA256, AES256GCM/SHA384)×two groups(X25519, P256)×three identities(RSA2048, RSA4096, ECDSA-P256)=12. Each has one-leaf and legal eight-certificate/64 KiB chain shapes, individual certificate≤16 KiB. Independent trust anchors and valid key/signature constraints are required. Add frontend fresh TLS+GET for12×2chains×populations1/64=48 rows. Add origin-client-role fresh HTTPS proxy GET for those12×2chains×populations1/64=48 rows, using clear frontend. The two roles are distinct, not assumed equivalent.

Data-record supplements use four settings: small/1/fresh, small/64/retained, maximum/1/retained, maximum/64/retained. Frontend AES256 bulk for four families(static GET, fixed-origin GET, fixed-body echo, chunked echo) adds16 rows; baseline AES128 remains. TLS-origin bulk uses both ciphers×three proxy families×four settings=24 rows. Joint maximum frontend and origin RSA4096/P256/AES256/max-chain profile uses three proxy families×populations1/64×fresh/retained=12 rows. Total146+48+48+16+24+12=294 ordinary cohorts, including explicitly repeated baseline anchors in role supplements for order/fixture control.

Pipeline supplement: four independent-request families(static GET, proxy GET, fixed-body echo, chunked-body echo)×two baseline frontend transports×sizes16 KiB/maximum×populations1/64×fresh/retained=64 rows. Each complete cycle contains a depth-eight pipeline and all eight ordered complete replies; HEAD/validator-dependent cycles are not falsely pipelined before their prerequisites exist. Fresh means one pipeline cycle/new client connection, retained means two complete pipeline cycles per measured lifetime. Only64 requests are active at once and queued/pending/global budgets remain; all 512maximum responses need not coexist. Joint expensive TLS and sustained largest/unread-state cohorts also exercise depth-eight, without extra rows. Ordinary total 294+64=358, sustained32.

Grouping rationale: fixed public behavior is separately tested for every form; throughput rows retain each message family and finite size/concurrency/reuse extremes. Asymmetric key/group/chain work occurs at setup, covered for every declared configuration in **each** TLS role. Bulk record work varies with cipher and bytes, explicitly separated; it does not re-validate a certificate on every record. Repeated lifetime setup is nevertheless charged in fresh/retained complete cycles. Compound maxima check costly setup with largest traffic and both roles. This is a predeclared coverage argument, not a measurement or assertion every unseen algorithm/workload interaction costs the same. Evidence of a material omitted interaction reopens the matrix before qualification. IPv4 is the comparison path; IPv6 functional parity is mandatory, and a future IPv6 performance claim needs its own explicit environment/matrix.
